# IM 实时通信模块分析报告

## 一、v1.1 版本基线分析

### 1.1 版本定位

v1.1 是聊天模块从基础业务接口向实时通信系统演进的第一版稳定基线，核心目标不是追求极限吞吐，而是建立完整的“连接—鉴权—发送—落库—确认—推送—重连—同步”闭环。

该版本已经具备以下能力：

- Spring WebSocket 与 Netty 双接入能力，为后续按部署环境或灰度策略切换传输层保留空间。
- 基于 Redis 的会话消息序号分配，避免同一会话依赖数据库自增或行锁完成顺序控制。
- 消息发送确认、持久化确认和失败重试语义，客户端可以根据 ACK 判断消息是否已经进入服务端处理链路。
- RabbitMQ 持久化投递、重试和死信队列能力，用于解耦消息持久化与实时推送等派生事件。
- Redis 会话级限流、在线状态和未读数缓存，保护数据库并支撑高频连接状态更新。
- 断线重连后的消息同步接口，避免客户端只依赖实时推送而丢失离线期间消息。

从系统职责看，v1.1 解决的是“消息能够可靠地发送和恢复”；v1.2 则进一步解决“消息如何分片、如何在组件故障后补偿，以及如何对一致性和容量进行验证”。

### 1.2 v1.1 总体架构

v1.1 的逻辑链路可以概括为：

```text
客户端
  │
  ├── HTTP：获取 WebSocket Ticket、发送消息、同步历史消息
  │
  └── WebSocket：建立长连接、发送聊天帧、接收 ACK/推送/心跳
          │
          ▼
      Gateway / Chat Service
          │
          ├── 身份鉴权与 Ticket 校验
          ├── 会话成员和业务身份校验
          ├── Redis 原子分配 conversationSeq
          ├── MySQL 持久化 chat_message
          ├── RabbitMQ 异步投递派生事件
          ├── Redis 未读数、在线状态和限流
          └── WebSocket 连接注册表与发送队列
          │
          ├── 在线用户：实时推送
          └── 离线/重连用户：/chat/message/sync 补偿
```

v1.1 的关键设计原则是将“消息持久化”和“实时在线状态”分离：数据库保存消息事实，Redis 保存高频状态，RabbitMQ 负责异步事件传递，WebSocket 只承担实时交互，不作为离线消息的唯一来源。

### 1.3 传输层设计

#### Spring WebSocket 接入

Spring WebSocket 主要承担标准化 WebSocket 接入和业务集成职责，便于快速接入现有 Spring 鉴权、Controller 和业务服务。其优势是开发成本低、与 Spring 生命周期和安全体系集成简单；不足是连接状态、写操作并发和慢客户端背压需要额外封装。

#### Netty 接入

Netty 作为高并发传输层，使用 EventLoop 管理连接状态和网络写操作，将可能阻塞的聊天业务交给独立 Worker 执行。这样可以避免数据库、Redis 或 RabbitMQ 操作阻塞网络线程，并为后续连接级水位线、发送队列和连接回收提供更细粒度的控制。

两种接入方式共享消息服务层、Redis 序号分配、数据库持久化、RabbitMQ 事件投递和同步接口，传输层的差异不会改变业务消息语义。

### 1.4 WebSocket 协议与帧语义

客户端建立连接前先通过 HTTP 获取一次性 Ticket，连接时携带 Ticket 或由网关完成身份注入。连接成功后，客户端和服务端通过带版本号、请求号和消息类型的 JSON 帧通信。

典型客户端发送帧包含：

```json
{
  "version": 1,
  "requestId": "唯一请求号",
  "type": "chat",
  "data": {
    "sessionId": "会话 ID",
    "clientMessageId": "客户端幂等 ID",
    "type": 0,
    "content": "消息内容"
  }
}
```

服务端主要返回以下事件：

- `chat_accepted`：服务端已接收并开始处理消息，表示请求进入业务链路，不等同于数据库提交完成。
- `chat_ack`：消息已经完成持久化确认，客户端可将本地消息标记为服务端已确认。
- `chat`：接收方收到的实时消息推送，包含 `messageId`、`clientMessageId` 和 `conversationSeq`。
- `heart_beat` / `pong`：连接保活和链路健康检查。
- `error`：参数、鉴权、限流、会话状态或服务端处理失败。

这种 ACK 分层语义避免客户端把“网络连接成功”“服务端收到请求”和“消息已经持久化”混为一谈，也为超时重试和断线同步提供判断依据。

### 1.5 消息发送链路

v1.1 一条消息的典型处理顺序如下：

1. 客户端生成唯一 `clientMessageId` 并发送消息帧。
2. 服务端基于 Ticket 和服务端用户身份确认发送者，不能信任客户端伪造的身份字段。
3. 校验会话存在性、会话成员关系、对端用户身份和消息内容合法性。
4. 使用 Redis 原子序列分配器为会话分配 `conversationSeq`。
5. 以 `(sender_id, client_message_id)` 做幂等查询，重复请求返回已有消息而不是重复落库。
6. 将消息写入 `chat_message`，保存发送者、接收者、会话、序号、类型、内容和访问状态。
7. 在提交确认后返回 `chat_ack`，并异步产生实时推送、未读数刷新和会话索引等派生事件。
8. 接收方在线时由连接注册表找到目标连接并进入发送队列；离线时由同步接口在重连后补回。

v1.1 的消息事实来源是 MySQL，Redis 和 RabbitMQ 中的数据都属于可重建或可重试的派生状态。这个分层使得实时推送失败不会直接等价为消息丢失。

### 1.6 消息状态与发送语义

从业务角度，消息可以抽象为以下状态：

```text
accepted → persisted → delivered → read
```

- `accepted`：服务端已接受请求并完成基础校验。
- `persisted`：消息已写入数据库，具备可恢复事实。
- `delivered`：消息已通过实时推送或断线后的同步接口到达接收方。
- `read`：接收方已确认阅读，更新已读序号或已读状态。

v1.1 的主要可靠性边界在于：数据库持久化与异步派生事件并非同一个物理事务。因此系统依赖消息 ACK、RabbitMQ 重试、客户端超时重发、同步接口和未读校准共同形成最终一致性闭环。

### 1.7 Redis 在 v1.1 中的职责

Redis 并非单一缓存，而是承担多个高频、低延迟职责：

- **会话序号：** 通过原子递增或 Lua 脚本分配 `conversationSeq`，避免并发发送时出现重复序号。
- **在线状态：** 保存用户或连接的在线信息，配合 CAS 或过期时间避免旧连接误删新连接状态。
- **未读数：** 保存接收方在会话维度的未读数量，降低每次推送都访问数据库的成本。
- **会话级限流：** 使用令牌桶等机制限制热点会话的发送速率，防止单一会话拖垮数据库。
- **Ticket：** 保存一次性或短时有效的 WebSocket Ticket，连接身份以服务端 Ticket 内容为准。

Redis 数据丢失后，消息正文可以从 MySQL 恢复；序号、未读数和在线状态则需要通过数据库最大序号、已读序号、连接重建和校准任务恢复。

### 1.8 RabbitMQ 与可靠事件

RabbitMQ 用于承载消息写入后的异步派生事件，将实时推送和缓存更新从发送请求中解耦。典型事件包括：

- 接收方实时推送；
- 接收方未读数刷新；
- 发送方和接收方会话索引更新；
- 持久化失败重试和死信处理。

v1.1 已具备持久化队列、消费失败重试和 DLQ 思路，但消息数据库写入与事件表/Outbox 的原子性仍存在边界，这也是 v1.2 引入 Outbox、Claim Token、对账和补偿机制的主要原因。

### 1.9 断线重连与消息同步

客户端断线后不能只依赖 WebSocket 重连期间的实时事件，因为连接断开期间可能发生消息推送失败、客户端进程重启或网络重传。v1.1 通过同步接口补齐这段窗口：

```http
POST /chat/message/sync
```

请求携带 `sessionId`、上次收到的 `afterConversationSeq` 和分页数量。服务端按会话序号升序返回之后的消息，客户端通过 `clientMessageId` 或 `messageId` 去重，并更新本地最大 `conversationSeq`。

同步接口的核心保证是：实时推送可以重复或丢失，但只要消息已经落库，客户端最终可以通过同步接口恢复；因此客户端必须持久化最后确认的会话序号，并在重连后主动同步。

### 1.10 v1.1 性能基线

v1.1 基线来自本机 Docker 环境下的聊天消息发送测试，测试重点为单热点会话保护和消息发送接口延迟：

| 指标 | v1.1 基线 |
|---|---:|
| 成功率 | 约 99.97% |
| HTTP P95 | 32.92ms |
| HTTP P99 | 59.8ms |
| 测试场景 | 单热点会话持续发送 |

该基线说明 v1.1 在中等负载下具备可用的发送延迟，但单库写入、同步派生事件、单会话限流和缺少物理分片会限制横向扩展能力。v1.2 的优化数据应与 v1.1 作为同口径趋势参考，不应把不同测试时长、部署拓扑和宿主机状态下的结果直接当作严格回归结论。

### 1.11 v1.1 设计亮点

1. **双 WebSocket 接入设计：** 在保留 Spring 生态开发效率的同时引入 Netty，为高并发连接治理和后续传输层切换提供基础。
2. **Redis 原子序号：** 把热点会话序号分配从数据库行锁竞争中分离出来，降低并发写入时的锁等待。
3. **客户端幂等标识：** 使用 `clientMessageId` 支持超时重发和重复请求去重，避免网络重试造成重复消息。
4. **ACK 与同步接口结合：** 将在线实时性和离线可靠性拆开，允许客户端在连接恢复后主动补偿。
5. **RabbitMQ 异步解耦：** 将推送、未读数和会话索引等非核心写入动作从发送主链路中拆出。
6. **Redis 限流与未读缓存：** 对热点会话提供保护，同时降低高频未读查询对数据库的压力。

### 1.12 v1.1 的主要问题与演进动因

| v1.1 边界 | 风险 | v1.2 演进方向 |
|---|---|---|
| 消息集中存储在单库 | 写入和容量扩展受单库约束 | 32 逻辑分片、虚拟桶和灰度迁移 |
| 消息与派生事件存在跨组件窗口 | 可能出现已落库但事件缺失 | Outbox、对账、重叠窗口和幂等补偿 |
| 实时推送依赖连接状态 | 慢客户端可能积压内存或阻塞写操作 | 有界队列、水位线、背压和 4008 关闭码 |
| 仅有成功率和延迟指标不足 | 无法证明落库、同步和序号一致 | 10K 级发送—落库—同步闭环校验 |
| 单会话限流与整体吞吐容易混淆 | 错误评估服务真实容量 | 单热点保护与多会话吞吐分开测试 |
| 单调游标可能漏掉小 ID 晚提交 | 对账任务存在盲区 | 事务 A/B 验证和 100 条重叠扫描窗口 |

### 1.13 v1.1 结论

v1.1 已经完成从普通 WebSocket 聊天接口到具备 ACK、幂等、序号、重连同步和异步事件能力的实时消息系统的关键跨越。其核心价值是建立正确的消息语义和恢复路径，而不是单纯提高单机吞吐。

从工程演进角度，v1.1 的设计为 v1.2 提供了三个重要基础：一是可复用的消息状态和协议语义，二是 Redis/RabbitMQ/MySQL 的职责边界，三是通过同步和重试弥补实时连接不可靠性的机制。v1.2 在此基础上补齐了分片、Outbox、故障注入、一致性对账和游标盲区修复。

## 二、v1.2 升级与验证

v1.2 在 v1.1 的 Spring WebSocket + Netty 双接入、Redis 会话序号、消息 ACK/重推、RabbitMQ DLQ、Redis 限流和未读数校准基础上，进一步完成了消息存储分片、异步事件投递、故障恢复和运维安全治理。

本版本的核心变化是：聊天模块从“单库实时通信服务”升级为“支持物理分片、最终一致性和可恢复运维的消息系统”。

## 三、主要升级

### 1. 消息物理分片与灰度迁移

- 增加 `LEGACY_ONLY`、`DUAL_WRITE`、`SHARD_ONLY` 三种存储模式。
- 使用 1024 个虚拟桶，将会话稳定路由到物理分片，保证同一会话的消息落在同一分片。
- 当前支持 32 个逻辑分片，按配置映射到多个 MySQL 实例。
- 增加分片数据源、分片表、历史数据回填、数据校验和读旧表 fallback。
- 支持从旧表双写逐步切换到 `SHARD_ONLY`，降低一次性迁移风险。
- 分片表成为 `SHARD_ONLY` 模式下消息数据的唯一事实来源。

### 2. 消息写入链路优化

- 保留 Redis 原子序号分配，避免热点会话使用数据库行锁串行分配消息序号。
- 分片写路径关闭 Seata 全局事务，减少热路径事务开销。
- Outbox 写入移出发送临界路径，采用有界异步队列处理派生事件。
- 优化分片连接池，当前压测配置为每个分片最大 40 个连接。
- 幂等查询支持关闭旧表 fallback，避免每条新消息额外查询一次旧表。
- 对端用户查询增加本地参与者缓存，减少重复数据库读取。

### 3. Outbox、重试和故障恢复

- 增加消息 Outbox，统一承载在线推送、未读数刷新和会话索引更新事件。
- 使用 Claim Token 防止多个 Worker 重复处理同一批事件。
- 支持批量 Claim、并行派发和派生事件合并，降低主库写放大。
- 事件失败后按退避策略重试，超过最大次数进入终态失败状态。
- 增加 DLQ Replay 运维能力。
- 增加 Outbox 定时清理和消息源对账任务。
- 当消息已落库但 Outbox 事件未成功生成时，可通过游标对账重新补偿事件。

### 4. WebSocket 连接治理

- Spring WebSocket 和 Netty 连接均使用有界发送队列，避免 RabbitMQ 消费线程或业务线程直接并发写 WebSocketSession。
- Netty 使用 EventLoop 管理连接状态和写操作，并使用独立 Worker 执行阻塞型聊天业务。
- 增加连接级消息数和字节数上限。
- 增加 Netty 写缓冲区高低水位线，实现慢客户端背压。
- 连接发送队列超过上限时使用关闭码 `4008`，客户端通过消息同步接口恢复断线期间的消息。
- 继续使用 HashedWheelTimer 管理空闲连接，并通过超时校验、幂等关闭和 Redis CAS 避免误关闭及在线状态误删。

#### Netty 直连实测

使用 k6 从 Docker 内部网络直连 Netty，补齐协议要求的 `version` 和 `requestId` 后完成 500/1000/2000 并发测试。三档测试的握手与心跳成功率均为 100%。

| 并发连接 | 建连 P95 | 建连 P99 | 握手成功率 | 心跳成功率 |
|---:|---:|---:|---:|---:|
| 500 | 1.02ms | 3.05ms | 100% | 100% |
| 1000 | 1.08ms | 6.24ms | 100% | 100% |
| 2000 | 1.99ms | 8.29ms | 100% | 100% |

### 5. 安全与运维治理

- WebSocket 使用 Redis 校验一次性 ticket，ticket 身份作为连接身份唯一来源。
- 忽略客户端伪造的 `userId` 和 `userFrom` 请求头，网关转发时清理可伪造身份头。
- Actuator 的 health/info 保持可探活，其余 Prometheus、连接池检查和 DLQ Replay 接口需要 `X-Actuator-Token`。
- 未配置 Actuator token 时，敏感运维接口默认拒绝访问。
- 增加主库和分片连接池的 active、idle、pending、timeout 指标。
- 保留 Prometheus 指标：在线连接数、发送延迟、落库延迟、同步延迟、推送失败和限流次数。

### 6. 业务能力扩展

- 增加 Agent 会话创建和 Agent 消息发送能力。
- 增加内部服务查询会话上下文的接口。
- 支持法律 Agent 与聊天会话关联。
- 增加内容审核、参与者身份校验、用户资料查询和房源发布关联能力。

## 四、性能实测

### 3.1 热点会话测试

测试环境：当前本机 Docker 开发环境，chat 服务运行在 `SHARD_ONLY + 物理分片` 模式，使用 k6，单热点会话，目标速率 40 msg/s，测试约 50 秒（含升压和降压阶段）。

| 指标 | v1.1 基线 | v1.2 实测 | 变化 |
|---|---:|---:|---:|
| 成功率 | 约 99.97% | 100% | 提升 |
| P95 | 32.92ms | 19.46ms | 约下降 41% |
| P99 | 59.8ms | 34.79ms | 约下降 42% |
| 完成请求 | — | 1,604 | — |
| dropped iteration | — | 0 | — |

### 3.2 多会话吞吐测试

为避免单会话限流影响结果，使用 31 个测试会话分摊请求，目标速率 100 msg/s，测试约 50 秒（含升压和降压阶段）。

| 指标 | v1.2 实测 |
|---|---:|
| 成功率 | 100% |
| 完成请求 | 4,004 |
| P95 | 27.85ms |
| P99 | 41.06ms |
| 最大延迟 | 99.94ms |
| dropped iteration | 0 |

### 3.3 单会话限流说明

单热点会话直接压测 100 msg/s 时，约 34% 请求被拒绝，但成功请求的 P95 仍为 17.9ms、P99 为 25.85ms。该现象是 Redis 会话级令牌桶主动保护数据库，并非服务处理能力耗尽。

因此，评估整体吞吐时应使用多会话测试；评估热点保护时应单独观察限流计数和拒绝比例。

## 十、故障场景验证记录

### 9.1 杀 Chat Worker

测试过程中先发送一条故障前消息，然后使用 `docker kill -s KILL frameworkjava-chat` 强制终止 Chat Worker，再启动同名容器并等待 18083 端口和应用恢复。恢复后再次发送一条消息，并查询数据库确认两条消息均已落库。

结果：Chat 容器恢复成功，故障前后消息落库数为 `2/2`，场景通过。该结果证明 Worker 进程被强制终止后，服务可以重新建立连接并继续处理新的消息；本轮没有把正在 Worker 内存中的未提交请求宣称为必然不丢失，生产验证仍应配合客户端重试和消息账本进行确认。

### 9.2 重启 RabbitMQ

发送故障前消息后执行 `docker restart frameworkjava-rabbitmq`，等待 RabbitMQ 恢复，再发送故障后消息。RabbitMQ 重启期间 Chat 服务保持可恢复，恢复后健康状态最终为 `healthy`；两条消息均成功落库，并各自存在 Outbox 关联记录。

结果：消息落库数为 `2/2`，Outbox 关联消息数为 `2/2`，场景通过。该结果验证 RabbitMQ 短暂重启后，消息发送链路可以恢复；本轮未模拟长时间 MQ 不可用、生产者 confirm 超时和大规模积压，不能外推为 MQ 集群级 HA 结论。

### 9.3 Outbox 事件缺失与对账补偿

先发送测试消息，确认该消息已有 4 条 Outbox 事件；随后只删除该消息对应的 Outbox 行，模拟“消息已落库但 Outbox 事件缺失”。第一次等待 35 秒后，Outbox 行仍为 `0`，说明当前实现使用持久化游标增量扫描时，如果游标已经越过该消息，删除已处理消息的 Outbox 行不会被自动回溯发现。

随后将本次测试对应的 `legacy` 对账游标回退到该消息 ID 之前，重新触发定时对账。约 9 秒内恢复为 4 条 Outbox 事件，证明对账补偿逻辑本身可以补齐缺失事件。

结果：

| 子场景 | 删除后 | 对账后 | 结论 |
|---|---:|---:|---|
| 游标已越过消息，直接删除 Outbox | 0 | 0 | ❌ 暴露回溯边界 |
| 游标回退到消息之前后再对账 | 0 | 4 | ✅ 补偿机制有效 |

该场景应标记为“部分通过”：当前补偿任务能够修复游标覆盖范围内的缺失事件，但不能发现已经被游标确认过、随后才发生的 Outbox 删除。生产设计建议增加周期性重叠窗口、按消息存在性反查 Outbox，或增加独立的 Outbox 完整性巡检，避免单一增量游标成为补偿盲区。

## 十二、游标盲区修复与事务 A/B 迟到提交验证

### 11.1 修复方案

对账游标不再只查询 `id > last_message_id`，每轮会从游标之前回看固定数量的消息 ID。当前默认重叠窗口为 100 条，可通过 `CHAT_OUTBOX_RECONCILE_OVERLAP_MESSAGES` 调整：

```yaml
chat.outbox.reconcile-overlap-messages: ${CHAT_OUTBOX_RECONCILE_OVERLAP_MESSAGES:100}
```

重叠扫描会重复读取一小段已处理消息，但 Outbox 使用 `(message_id,event_type,recipient_id)` 唯一键，重复扫描只执行幂等插入，不会产生重复推送、重复未读刷新或重复会话索引副作用。

### 11.2 事务 A/B 测试

测试脚本：`deploy/perf/chat-transaction-ab-late-commit.ps1`。运行标识：`transaction-ab-20261021-232319`。测试使用物理分片 `shard-31`：
