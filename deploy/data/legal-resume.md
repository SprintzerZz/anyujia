# anyujia-legal 法律智能 Agent：简历项目描述

## 一句话项目概述

面向租客签约场景设计并实现法律风险分析 Agent：租客在租客/房东聊天页点击“法律助手”后创建独立会话，系统综合分析 Apache Tika 解析的合同、聊天事实、房源发布信息和法规 RAG 内容，输出可追溯的风险判断、证据引用和降级结果。

## STAR 项目经历

### S｜项目背景

租客在签约前需要同时核对合同条款、房东在聊天中的承诺、房源发布信息和适用法规。原有链路存在同步处理耗时长、上下文容易被截断、外部依赖失败影响主流程、任务状态依赖单实例内存、SSE 长连接占用业务线程等问题，难以支撑可审计和可恢复的生产级法律 Agent。

### T｜负责目标

- 设计租客私有的法律助手独立会话，隔离原始租客/房东聊天。
- 建立合同解析、风险识别、RAG 检索、AI 增强、证据引用和结果通知的完整链路。
- 将评估任务从本地异步执行升级为数据库持久化、跨实例租约接管、幂等重试和失败恢复模型。
- 解决 SSE 长连接与 Agent Worker、数据库轮询和慢客户端之间的资源竞争。
- 建立离线评估集和可验证指标，避免以未经验证的压测数字作为生产容量结论。

### A｜关键行动

#### 1. 搭建多源证据驱动的法律 Agent 链路

- 使用 Apache Tika 作为 PDF/DOCX 正文解析的统一事实源；PDFBox 仅补充 PDF 加密检测、页数和页级定位，POI 仅补充 DOCX 结构定位。
- 以租户、聊天会话和合同 SHA-256 实现合同注册幂等，持久化合同元数据、解析 block 和证据定位信息。
- 将合同条款、聊天消息、房源快照和法规 passages 分开建模，避免将模型生成内容当作事实来源。
- 采用词法检索、法律意图检索、向量检索、RRF 融合和重排构建 RAG；Milvus、Embedding、Reranker、AI 或 Redis 不可用时回退到词法检索、抽取式回答或确定性规则。
- 对模型回答增加 citation allow-list，非法引用或越界引用时回退，保留降级原因和证据清单。

#### 2. 实现租客私有的独立 Agent 会话

- 在 Chat 模块新增 Agent 类型会话：租客点击法律助手后创建独立 `conversation_type=AGENT` 会话，原租客/房东会话只作为证据来源。
- 通过 `landlordConversationId + contractId` 绑定法律会话，校验租客、原始会话、合同和已有绑定关系，避免跨租户或错合同绑定。
- 将法律回答写回 Agent 独立会话，不污染租客与房东的原始对话；原始对话中的消息 ID、会话序号和发送者信息作为可追溯证据保留。

#### 3. 建立生产级异步任务可靠性模型

- 以 MySQL 持久化 `PENDING/RUNNING/COMPLETED/FAILED` 任务状态、`requestId`、租约持有人、租约过期时间、重试次数和下一次执行时间。
- 使用“带状态条件的原子领取”避免多实例重复执行；实例宕机或租约过期后由调度器重新置回待执行状态，实现任务接管。
- 引入 Outbox、RabbitMQ Consumer、Redis Stream 和事件表，将任务执行、结果事件和 SSE 连接解耦，支持断线后的 `Last-Event-ID` 增量重放。
- 任务完成后再进入 Chat 投递阶段，使用 `legal-agent-{taskId}` 作为稳定幂等键，重复投递返回同一条消息，不产生重复法律结论。
- 保存合同 hash、聊天消息 ID/序号、房源 ID、法规片段 ID、地区、日期、模型版本和提示词版本，形成 `evidence_manifest` 审计清单。

#### 4. 实现上下文压缩与过期答案阻断

- 合同按风险条款和 document block 结构压缩，优先保留押金、租金、维修、违约、解约、转租和退租条款，并保留 block/page/heading 定位。
- 聊天上下文提取金额、日期、责任主体和承诺，保留原始消息 ID 与会话序号；Agent 历史保留最近轮次，较早内容生成有界摘要。
- 对合同、聊天、房源、法规和 Agent 历史生成 SHA-256 上下文指纹，记录 `FIRST/UNCHANGED/CHANGED/UNKNOWN` 状态。
- 模型生成前后重新读取关键证据并复核 hash；合同或聊天在分析期间发生变化时标记 `STALE_CONTEXT`，不发布过期模型答案，提示用户重新分析或确认。

#### 5. 重构 SSE 与性能验证链路

- 将 SSE 从固定业务线程轮询改为共享调度器、Redis Stream 唤醒和独立 writer 线程池，连接不再占用 Agent Worker。
- 增加连接上限、心跳、断线重放、有界唤醒队列、慢客户端保护、写出拒绝和队列溢出指标。
- 通过 Gateway 验证“租户 Token → AuthFilter → Nacos 服务发现 → Legal Agent → SSE”完整链路，首事件为 `event:connected / data:ok`。
- 建立 7 个离线上下文评估用例，覆盖关键事实、证据引用、无关消息过滤、多轮历史、合同/聊天冲突和上下文变化。

### R｜结果与数据

以下数据均来自项目报告中的实际测试或离线评估；未验证的生产容量未写入为结论。

- RAG 检索评估集 34 例：Recall@4 **98.53%**、HitRate@4 **100%**、MRR **0.8578**、nDCG@4 **0.8809**，P95 **2401.13ms**。
- 法律问答评估集 37 例：citation validity **100%**、citation coverage **93.24%**、keyword coverage **89.19%**、scope compliance **94.59%**，P95 **706.69ms**。
- SSE 本地 1000 长连接复测：建连 P95 **26.37ms**、P99 **167.07ms**，达到报告设定的 P95 < 1s、P99 < 3s 目标。
- Gateway + SSE 完整链路：1000 个任务、10 秒斜坡建连，建连 P95 **22.75ms**、P99 **43.30ms**，覆盖鉴权、路由、Nacos 服务发现、SSE Writer 和心跳。
- Legal 模块定向测试多轮通过：SSE/任务链路阶段 **12/12**，上下文压缩与版本指纹阶段 **7/7**，PDF/DOCX 解析器阶段 **2/2**；Chat/Legal 聚合回归阶段报告记录 **11/11**。
- 通过 7 例冻结离线评估集校验证据召回、关键事实召回、无关证据误选和上下文状态；评估器会拒绝缺失预测、重复预测和不存在的引用 ID。
- 通过数据库持久化任务、租约接管、Outbox、事件重放和 Chat 幂等投递，消除“实例重启丢任务”和“重试产生重复法律消息”的主要风险。

## 面试展开要点

1. 为什么法律 Agent 使用 SSE 而不是直接复用 Chat WebSocket？

法律 Agent 是长耗时、低频、以任务结果为核心的单向通知场景；Chat WebSocket 适合租客与房东的高频双向消息。最终采用 HTTP 快速创建任务、Worker 异步分析、SSE 订阅状态和查询接口兜底，并复用 Chat 的事件驱动、幂等和补偿思想。

2. 如何避免模型回答基于过期合同？

分析前后重新读取合同、聊天和房源证据，计算上下文 hash 并比较；如果分析期间证据变化，标记 `STALE_CONTEXT/contextConflict=true`，不发布旧回答，提示重新分析或确认。

3. 如何保证任务不丢、结果不重复？

任务状态、租约和重试信息落 MySQL，实例通过原子条件更新领取；租约过期后重新入队。结果发送使用稳定 `requestId`，Chat 侧利用唯一键返回已存在消息，重复消费不会产生重复法律消息。

4. 压测数据如何避免夸大？

区分离线质量指标、SSE 建连指标和端到端入队/完成指标；报告中明确本地环境的入队 P95 约 6.6 秒不能作为产品容量承诺，同时记录数据库争用、VU 不足和 Gateway/依赖状态，只有真实 Gateway 链路和可复现实验才写入简历。
