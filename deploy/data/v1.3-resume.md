# IM 实时通信系统升级项目（简历版）

## 项目概述

负责将聊天模块从单库实时通信服务升级为基于 Netty、Redis、RabbitMQ 和 MySQL 物理分片的可扩展消息系统，重点解决高并发连接、消息顺序、可靠投递、故障恢复、数据一致性和灰度迁移问题。

技术栈：Java 17、Spring Boot、Netty、Redis、RabbitMQ、MySQL、Docker、k6、Prometheus。

## 项目经历（STAR）

### 1. 完成聊天消息存储分片与灰度迁移

- **Situation：** 原有聊天消息集中存储在单库，随着会话和消息量增长，数据库写入、序号分配和历史数据迁移逐渐成为扩展瓶颈。
- **Task：** 在不影响已有业务的前提下，将消息存储升级为可灰度切换的物理分片架构。
- **Action：** 设计 `LEGACY_ONLY`、`DUAL_WRITE`、`SHARD_ONLY` 三种迁移模式；使用 1024 个虚拟桶将会话稳定路由到 32 个逻辑分片，保证同一会话消息落在同一分片；补充分片数据源、历史回填、数据校验和旧表 fallback 能力，并通过配置实现平滑切换。
- **Result：** 完成从单库到 `SHARD_ONLY` 的灰度迁移路径，降低一次性切换风险；同一会话具备稳定路由和独立扩展能力，为后续水平扩容提供基础。

### 2. 优化高并发消息发送链路

- **Situation：** 消息发送链路包含序号分配、参与者校验、数据库写入和派生事件处理，容易因数据库锁竞争和同步 Outbox 写入导致请求延迟升高。
- **Task：** 降低发送热路径耗时，同时保持消息顺序、幂等和可靠投递。
- **Action：** 使用 Redis 原子操作分配会话序号，避免热点会话依赖数据库行锁；关闭分片写路径上的 Seata 全局事务；将 Outbox 写入移至有界异步队列，并结合 CallerRunsPolicy 实现背压；引入参与者本地缓存、分片连接池和批量事件 Claim 机制。
- **Result：** 单热点会话 40 msg/s 测试成功率达到 100%，P95 从 32.92ms 降至 19.46ms，P99 从 59.8ms 降至 34.79ms；多会话 100 msg/s 测试完成 4,004 次请求，成功率 100%，P95 27.85ms，P99 41.06ms。

### 3. 构建基于 Netty 的高并发 WebSocket 连接治理能力

- **Situation：** 高并发长连接场景下，连接写操作、慢客户端和空闲连接容易造成线程阻塞、内存增长及在线状态误判。
- **Task：** 提升 WebSocket 建连和消息写入的并发能力，并控制慢客户端对系统的影响。
- **Action：** 使用 Netty EventLoop 管理连接状态和写操作，使用独立 Worker 执行阻塞型业务；为连接配置有界发送队列、写缓冲区高低水位线、消息数/字节数上限和 `4008` 慢客户端关闭策略；通过 HashedWheelTimer、超时校验、幂等关闭和 Redis CAS 管理空闲连接与在线状态。
- **Result：** Netty 直连 500、1000、2000 并发测试的握手成功率和心跳成功率均为 100%；2000 并发建连 P95 为 1.99ms、P99 为 8.29ms，具备较低连接建立延迟和可控背压能力。

### 4. 建立 Outbox 可靠投递与故障补偿机制

- **Situation：** 消息落库与在线推送、未读刷新、会话索引更新存在跨组件故障窗口，可能出现消息已落库但事件缺失、重复消费或 Worker 重启后的数据不一致。
- **Task：** 保证消息事件最终可达、可重试、可补偿且重复执行不产生重复副作用。
- **Action：** 引入 Outbox 统一承载派生事件；使用 Claim Token、批量 Claim、并行派发、退避重试和 DLQ Replay 控制消费；增加消息源对账任务；针对游标盲区增加默认 100 条重叠扫描窗口，并利用 `(message_id,event_type,recipient_id)` 唯一键保证补偿幂等。
- **Result：** 30 条固定 `clientMessageId` 在 Worker 强杀后重试，最终 30/30 落库，重复消息、重复序号和序号空洞均为 0；RabbitMQ 停机期间发送 20 条消息，恢复后 Outbox pending 为 0，未读增量为 20；重复补偿后仍保持 4 条事件、重复副作用为 0。

### 5. 解决消息一致性与迟到提交问题

- **Situation：** 仅按单调消息 ID 推进对账游标时，事务 A 可能以较小 ID 延迟提交，事务 B 先提交并推进游标，导致事务 A 被后续增量扫描遗漏。
- **Task：** 复现并修复“小 ID 晚提交”造成的 Outbox 补偿盲区。
- **Action：** 构造事务 A/B 场景：事务 A 延迟提交较小 ID，事务 B 先提交较大 ID并推进分片游标；将对账查询改为回看游标前 100 条消息，并通过真实 MySQL 分片和定时对账任务验证补偿结果。
- **Result：** 事务 A 的消息 ID 为 `2112534771102429187`，晚于 ID `2112534771102429188` 的事务 B 提交；修复后 A、B 均补齐 4 条 Outbox，A 的重复副作用为 0，游标盲区未复现。

### 6. 建立可量化的压测与一致性验证体系

- **Situation：** 原有性能测试主要关注成功率和接口延迟，无法证明“发送、落库、推送/同步到达”之间没有丢失或重复。
- **Task：** 建立覆盖性能、持久化、同步补偿和序号完整性的闭环验证。
- **Action：** 使用 k6 进行多会话压测，为每条消息生成唯一 `clientMessageId`；压测后直接查询数据库、Outbox 和同步接口，校验发送数、落库数、同步到达数、重复消息、重复序号及序号空洞；将 Worker、RabbitMQ、迟到提交和重复补偿场景固化为 PowerShell 脚本并保存原始日志。
- **Result：** 10K 级测试实际完成 10,752 条消息，发送成功数、数据库落库数、同步回补数和 Outbox 关联数均为 10,752；31 个会话重复消息、重复序号和序号空洞均为 0。测试脚本和 JSON/日志产物可复现、可审计。

## 项目亮点总结

- 将聊天系统从单库架构升级为支持物理分片、灰度迁移和最终一致性治理的消息系统。
- 以 Netty EventLoop、有界队列、背压和独立 Worker 支撑高并发 WebSocket 连接治理。
- 通过 Outbox、重试、DLQ、对账和重叠窗口解决跨数据库、消息队列和实时推送链路的一致性问题。
- 用可量化压测和事务 A/B 故障注入验证设计效果，避免仅凭接口成功率判断系统可靠性。
