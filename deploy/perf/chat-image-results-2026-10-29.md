# 图片消息端到端压测（2026-10-29）

## 环境与口径

- Windows 本机 Docker Desktop；单个 chat 容器、单个 file 容器、MySQL、Redis Sentinel、RabbitMQ、SILO 对象存储。SILO 是维护中的 MinIO 分支，保留 S3 API 和 `MINIO_*` 配置；本次不是原 MinIO 官方镜像的性能结果。
- A 为用户 1，B 为用户 2，均属于会话 `900000000000100001`。图片为随机 RGB 内容的 256×256 PNG，196,992 字节。请求从本机访问 `127.0.0.1`，无公网传输和浏览器渲染时间。
- 发送使用 HTTP `/chat/message/send`；B 收取分别测 `/chat/message/sync` 和在线 WebSocket 推送；最后实际 GET 图片 URL 并核对字节数。当前 Web 前端使用 WebSocket 发送，因此这些数据不能直接等同于完整浏览器点击到渲染耗时。
- 每个并发档 20 次，WebSocket 单独测每档 10 次。2 次预热不计入同步读取样本。P95/P99 是小样本分位数，仅作本地基线。
- 上传限制为单 chat 节点同时 2 个；原始并发试验不重试。重试试验按前端策略最多 3 次，等待 250 ms、500 ms，并复用同一 `uploadId`。

## 结论与后续

- 单节点同时 2 个上传槽位可保护图片解码和存储，但 4、8 个突发上传会直接返回错误；当前前端重试在 8 并发下仍未消除失败。
- 稳定状态下，B 在线接收约 0.9 秒；主要等待在消息 outbox 的轮询和推送，上传本身通常约 0.1–0.2 秒。首轮 outbox 写入延后需排查异步队列及启动后历史任务积压。
- “上传过多”是预期背压，HTTP 500 容易被误判为服务故障；建议改为明确的限流响应，并在客户端展示重试状态。
- 数据来自本机单节点测试，不能外推至公网、移动网络、多节点或生产级对象存储。压测写入了开发库和对象存储中的测试消息与图片，未删除。

## 同日优化复测

修复内容：outbox 过期清理先走 `idx_chat_outbox_sent_cleanup` 取 ID，再按主键删除，避免旧 SQL 对约 90 万行做文件排序及长时间锁等待；轮询间隔从 1000 ms 调至 250 ms；单节点图片上传仍只有 2 个执行槽位，但允许最多 16 个请求等待 2 秒，超限返回 HTTP 429 / 业务码 `429000`。
